## The headline answer for this bucket

**No tool in this bucket lets one agent session see what another concurrent session is doing in one shared working tree. And the mainstream tools do the exact opposite on purpose.**

The dominant design, from the 9k-star worktree managers up to the 28k-star kanban front-ends, is **isolation**: one git worktree per agent, so sessions physically cannot collide. Their own READMEs say it out loud (verbatim quotes in the evidence section): "Nothing the agent does can collide with another task" (dev-3.0); "each pane is a full working copy, no conflicts between agents" (dmux); "Each task gets its own isolated git workspace, so no conflicts" (claude-squad); "five agents on five features at the same time, zero conflicts" (parallel-code); "Enable multiple agents to work safely and independently" (container-use). For that whole class a shared dirty working tree is not a supported use case - it is the problem they delete. They are the opposite strategy to ours, not a weaker version of it.

A second class (coordination layers: Foremerge, Concord, Grit, Who Broke It?, mcp_agent_mail, Guild, agentlocks, Traffic Control, MAK) DOES give concurrent sessions shared awareness. But **every one of them is cooperative**: awareness exists only because each agent voluntarily declares a claim, lease or intent through an MCP server, a CLI, or a hook. An agent that never calls the tool is invisible. None of them OBSERVE the repository. None of them read `git worktree list`, ref logs, or `git status --porcelain` to attribute work an agent did not announce. None of them compute hunk/line-range overlap from real edits. None of them split one mixed dirty tree into per-feature branches.

Named exceptions, closest first: **`naw103/foremerge`**, **`Get-Concord-AI/concord-mcp`**, **`andrefigueira/traffic-control`** - with **`simke9445/agentlocks`**, **`chaseungjoon/multi-agent-kernel`** and **`shriyashish-mishra/who-broke-it`** as the smaller near-hits. Full detail in "Surprises / collisions".

## Surprises / collisions

Ranked by how much they actually threaten our novelty. I would not want any of these buried in the README.

1. **`naw103/foremerge`** (538 stars, Apache-2.0, Rust, created 2026-08-21, last push 2026-10-04) - the single closest thing to our product, and it targets the same pain. Agents publish intent + semantic scope + operation into one shared SQLite store kept inside the project's `.git` folder, so "every agent on your machine sees the same picture, whether it is Claude, Codex, or Cursor"; a deterministic conflict detector then "names the two agents, explains why their plans clash, and suggests how to split the work", before either worktree changes. It already shares three of our stated properties: agent-neutral (Claude Code / Codex / Cursor), a deterministic data layer that explicitly refuses to let an LLM judge conflicts, and advisory-not-blocking warnings. It also goes **past** us on one axis we should not pretend otherwise: it catches semantic collisions between edits that touch *different files* (agent A replaces `PaymentService`, agent B extends it - no line overlap, real breakage). Pure line-range overlap cannot see that. **What still separates us, stated honestly:** (a) it is cooperative - the agent must publish intent, so a session that skips the protocol is invisible, while we derive everything from git plumbing whether or not the agent co-operates; (b) it never measures real edits, so it cannot report hunk/line-range overlap between two dirty trees; (c) it assumes isolated worktrees and says "coordination between machines is outside this project's scope"; (d) no dirty-tree -> per-feature-branch splitting; (e) Rust binary + MCP + SQLite, not stdlib-only Python. **Cite it by name.**
2. **`Get-Concord-AI/concord-mcp`** (456 stars, MIT, Node, created 2026-07-14, last push 2026-10-11) - cross-harness presence, direct cross-harness prompts/replies, file/module claims, and `start_work` which "reports scope overlaps before editing": a genuine pre-edit collision warning across Claude Code, Codex, Cursor, Gemini CLI, Grok Build and Goose. One SQLite store at the repo root, and it already follows git worktree `commondir` metadata so linked worktrees share one workspace. It also flags *stale claims* - an active claim whose owning agent disappeared - which is close to our session-liveness attribution. **Gaps:** cooperative claims, not observation; file/module granularity, not measured hunk/line-range; needs Node plus MCP registration written into every harness config; no dirty-tree -> per-feature-branch splitting; no grounded functionality brief built from git facts.
3. **`andrefigueira/traffic-control`** (2 stars, MIT, Go, created 2026-06-28) - tiny, but conceptually the closest to our **shared dirty tree** premise, and it frames our use case better than anyone in the bucket: several agents, one working tree, one live dev server and database, where "the agents are otherwise flying blind, and that is where work gets silently clobbered". A Go daemon ("the tower") tracks who is touching what; a `PreToolUse` hook requests clearance on every Edit/Write/MultiEdit and DENIES the write when another agent holds the path; `SessionStart` "checks the agent in and injects the current board into its context, so a fresh agent immediately knows who else is working and on what". That last item is our capability 4 in miniature. **Gaps:** file and recursive-glob leases, not hunk/line-range; cooperative hooks + MCP and Claude-Code-first (`tc install-claude`); a background daemon, which we are explicitly not; state lives in the tower rather than being read out of git, so it cannot see a session that never installed it and cannot attribute dirty files that already exist; no branch splitting.
4. **`shriyashish-mishra/who-broke-it`** (1 star, MIT, Go, created 2026-10-02 - ten days old) - the description is uncomfortably close to our pitch: "Task graph, intent and conflict detection, blast radius, verified handoffs, PR merge gate, git-native sync." It is a single static binary, "No server. No account.", "Requires only `git` at runtime", state as files in the repo, adapters for Claude Code / Codex / Cursor / OpenCode / Antigravity, MCP and CLI, and `wbi blame <path>` prints which **agent** and which task last changed a path plus the downstream tasks affected. That is our attribution + grounded-brief idea. **Gaps:** cooperative (a commit hook stamps task+agent and agents must follow the installed protocol); scope overlap is computed over declared task paths and contracts, not measured line ranges; fan-out is `wbi start TASK-001 --worktree`, i.e. worktree-per-task, not a shared dirty tree; no dirty-tree splitting; Go binary. Zero traction today, but the concept is a near-overlap and it is moving.
5. **`simke9445/agentlocks`** (11 stars, MIT, Node), **`luohoa97/agent-locks`** (0 stars, "no database, just markdown+YAML under `.git/`"), **`chaseungjoon/multi-agent-kernel`** (4 stars, Python) - three independent 2026 projects that reached the same "share ONE worktree and coordinate with leases/locks" conclusion, including one that is daemonless and file-based like ours and one (MAK) that arbitrates finer than a hunk, at tree-sitter symbol granularity, in a shared directory. The shared-tree coordination framing is no longer novel on its own. None of them observe git, do hunk-level overlap, produce a grounded brief, or split a dirty tree.

### Other things worth flagging

- **`rtk-ai/grit`** (118 stars, Apache-2.0, Rust) is the strongest *hard-locking* prior art: tree-sitter function-level claims, cross-agent blocking, worktree fan-out, serialised merges, published 50-agent benchmarks. If we ever write "nobody does sub-file conflict arbitration for agents", Grit and MAK refute it directly. Our defensible position is *advisory + observational + git-native + agent-neutral*, not *blocking + cooperative + daemon/cloud*.
- **`Jake-Network/radar`** (2 stars, Python, created 2026-10-09) refutes a weaker version of our pitch ("nobody predicts breakage before merge"). It is a local, no-API-key, no-daemon Python CLI that merges agent worktree branches in private git state and runs tests on the combination. Our differentiator has to be *static* hunk/line-range overlap on *uncommitted* work, not test execution on committed branches.
- **`Ataraxy-Labs/weave`** (1.3k stars) and **`Ataraxy-Labs/sem`** (3.4k stars) already own "tree-sitter entity-level granularity on top of git" and both are well-established. They are merge-time and single-actor, so they are complements, but a reader will ask how we relate and we should answer in one sentence.
- **`preset-io/agor`** (1.4k stars, BSL 1.1) is the closest thing to cross-session visibility in the mainstream tools - but the visibility is for *humans* reading a shared board, not for agents, and it runs on its own server/DB rather than on git facts.
- **`herdrdev/herdr`** (43.4k stars) is by far the biggest neighbour and already exposes an agent-facing CLI + socket API where "agents can spawn panes, prompt each other, and wait until another agent is genuinely blocked". If herdr ever adds repository-level (rather than pane-level) awareness it swamps this space. Today it has no file or hunk collision concept.
- **`Dicklesworthstone/mcp_agent_mail`** (2.2k stars) is the most-adopted advisory-lease layer, and its own docs call the leases "advisory" and "voluntary" - exactly the gap our observation-first design fills.
- **Nothing in this bucket does dirty-tree -> per-feature-branch splitting.** Searches for `split working tree into branches`, `uncommitted changes per feature branch`, `git stash per agent`, `dirty working tree split commits` returned 0 relevant repos. That capability still looks clear.
- **Nothing in this bucket derives awareness from git plumbing without agent co-operation.** Searches for `git-native agent coordination no daemon`, `observe agent activity repository git plumbing`, `which agent edited this file`, `agent brief other sessions repository` returned 0 relevant repos. That is our strongest remaining differentiator.
- **Hunk/line-range overlap prediction before merge** appears unclaimed. The only line/entity-granularity tools (`weave`, `sem`, `grit`, MAK) act at merge time or at write-lock time, never as a pre-merge prediction from two sets of uncommitted edits.
