# Prior art - Bucket 3: classic multi-session git/VCS coordination

Fetched 2026-10-12 with `/home/rk/Projects/priorart.py` (GitHub REST + PyPI JSON + primary docs).
Star counts and dates come from a `pa.repo()` call on that date. Docs quotes are verbatim.
Section "Local experiments" contains claims I verified by running git on this machine (git 2.25.1).

## The headline answer for this bucket

The classic tools give us **the substrate and the primitives, and none of them give us the layer**.
`git worktree` shares `refs/` across every linked worktree, `git stash` and branch reflogs live in the
common dir, and `git notes` attaches metadata to commits - so everything our tool reads already exists
and is already visible across sessions. What does not exist anywhere in this bucket is (a) attribution of
*uncommitted* edits to a session, (b) a warning before an edit or before a merge that two sessions are in
the same lines, and (c) turning one mixed dirty tree into per-feature branches.

Two honest concessions this bucket forces on us:
1. **Pre-merge conflict prediction is not new.** `git merge-tree --write-tree` (git >= 2.38) and
   git-branchless "speculative merges" both predict conflicts without touching the working copy.
2. **Lock-modify-unlock vs. optimistic concurrency is a 1979 debate, not our idea.** Our design is
   optimistic concurrency control (detect at merge, never lock) applied to a git repository. Say so.

## Notes and evidence

- `git/git`: `pa.repo` 2026-10-12 -> 63,819 stars, pushed 2026-10-12. `git-scm.com/docs/git-worktree` header: "git-worktree last updated in 2.56.0 / 2026-09-28".
- `git worktree` manpage, REFS section, verbatim: "In general, all pseudo refs are per-worktree and all refs starting with `refs/` are shared. There are exceptions, however: refs inside `refs/bisect`, `refs/worktree` and `refs/rewritten` are not shared." ## Local experiments (run on this machine, git 2.25.1, 2026-10-12)

These are the load-bearing premises of our tool, checked rather than asserted.

1. **A custom ref namespace is visible from every linked worktree.** `git update-ref refs/agentstate/sess-1 <sha>` in the main worktree; `git for-each-ref refs/agentstate` from `wt-a` printed the same sha, while `HEAD` differed (`master` vs `feat-a`). So a git-native, server-free, per-session state channel exists today.
2. **`git stash` is shared across worktrees.** After `git stash push -qm from-main` in the main worktree, `git stash list` in `wt-a` printed `stash@{0}: On master: from-main`, and `git rev-parse refs/stash` matched in both. Cross-session channel, zero attribution - it can equally protect or destroy another session's work.
3. **Branch reflogs are shared, `HEAD` is not.** `git reflog show master` from `wt-a` showed the commit made in the main worktree; `logs/refs/heads/{master,feat-b}` live under `git rev-parse --git-common-dir`; `git rev-parse --git-path HEAD` resolved to `.git/HEAD` in the main worktree and `.git/worktrees/wt-a/HEAD` in the linked one.
4. **A shared dirty tree carries no session identity whatsoever.** Three simulated sessions appended to `auth.py`, `api.py`, `ui.py` in ONE worktree. `git status --porcelain=v2 -uall` output was three lines of `1 .M N... <mode> <mode> <mode> <preimage> <image> <path>` - no author, no session, no feature. `git diff --stat` said only `api.py | 1 +`, `auth.py | 2 ++`, `ui.py | 1 +`. `GIT_AUTHOR_NAME` was empty in the editing environment. `git blame` on the dirty file reported `00000000 (Not Committed Yet ...)` for every uncommitted line. **This is the gap we are filling, and it is a property of git, not an oversight of one tool.**
5. **`git merge-tree --write-tree` needs git >= 2.38.** On this machine's git 2.25.1 the command rejected `--write-tree` with `usage: git merge-tree <base-tree> <branch1> <branch2>`. Any README claim built on it must state the version floor, and a stdlib-only tool must degrade to `git merge-file`/`diff3` or refuse on old git.

## Surprises / collisions

- **`git-branchless` speculative merge is real prior art for "predict the conflict without touching the tree".** If we write "nobody warns before the merge", that sentence is false. The defensible version is: prediction over **uncommitted** edits, attributed to **sessions**, at **line-range** granularity, across **harnesses**.
- **`jj absorb` / `sl absorb` / `hg absorb` are the closest existing automation of "route these hunks somewhere sensible".** All three route into *existing* commits in one author's stack. None of them creates per-feature branches, and none of them is aware of a second session. Our dirty-tree splitter must be described as "absorb, but the destinations are new per-feature branches and the hunks came from several authors", or reviewers will call it a re-skin of absorb.
- **`jj` is the tool a knowledgeable reviewer will name first**, because it shares one store across workspaces and deletes the dirty/committed boundary. The honest answer is that jj is single-actor by construction: one `@` per workspace, whole-tree snapshot on every command, one working-copy lock. It makes a shared dirty tree *more* dangerous, not less.
- **`git lfs lock` is the only shipped "declare your edit" mechanism in the git world**, and it is pessimistic and server-side. Our advisory/local/offline stance is a genuine difference, but it is a stance in a 40-year-old design debate, not a discovery.
- **Nothing in this bucket has a session concept.** Not git, not jj, not branchless, not Sapling, not hg. The word "session" does not appear as a first-class object in any of these models. That is the cleanest, most defensible sentence in our README - and it is a statement about a missing *data model*, not about a missing feature.
