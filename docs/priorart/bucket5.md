# Prior art — BUCKET 5: dirty-tree → per-feature commits/branches, and commit hygiene

Compared against the tool in `PRIORART_BRIEF.md`: a stdlib-only, git-based CLI that observes
refs/worktrees/dirty files, attributes work to agent sessions, detects file- **and hunk-level**
collisions before a merge, emits a grounded brief of what is being built elsewhere, and
orchestrates integration — including **splitting one mixed dirty tree into per-feature branches**.

All star counts and dates fetched live from the GitHub API / npm / PyPI on **2026-10-12** via
`priorart.py`. Descriptions are quoted verbatim from the API `description` field.

## The blunt answer to the bucket question

**Is there an existing tool that takes ONE dirty working tree containing interleaved work from
multiple features/sessions and automatically produces N per-feature branches with the right hunks
on each? No. Nothing found does it automatically.**

The ladder of closeness, from furthest to nearest:

1. **Hunk-level staging is manual.** `git add -p` (`s` to split a hunk, `e` to edit it), lazygit,
   gitui, tig, magit section staging, `cwarden/git-add--interactive`. All of them make a human
   decide, one hunk at a time, where each hunk goes. None creates branches.
2. **The built-in dirty-tree→branch recipe exists but is fully manual.** `git stash push -p`
   (selected hunks) then `git stash branch <name>` per feature. No grouping intelligence at all.
3. **`git-absorb` (5.7k stars) and `jj absorb` (32k stars) are the nearest *automation*.** Both
   assign hunks automatically by **line provenance** — "finds a changeset modifying those lines" /
   "moves each change to the closest mutable ancestor where the corresponding lines were modified
   last". That is the exact inference engine our splitter needs. But their targets are **existing
   commits in one branch's history**, not new per-feature branches, and the input is the staged
   diff on top of a branch you already own. `jj split --parallel` gets closest to sibling
   per-feature commits, and it is an interactive diff-editor.
4. **`ahnaf-lab/git-splice` (0 stars, 2026-10-04) is the nearest *mechanism* match**: stdlib-only
   Python, parses the working-tree diff into hunks, builds a hunk-adjacency + shared-identifier
   graph, deterministically clusters into independently-applicable patch sets. It stops at a commit
   stack on the current branch.
5. **`danieldelcore/diff-split` (3 stars, 2026-04-24) is the nearest *output* match**: one big diff
   → N clean PR branches, local git only, patch snapshots, a session branch for recoverability,
   cherry-pick per batch. It refuses to run unless everything is staged and nothing is unstaged,
   and it groups by package/team/N.
6. **GitButler (21.8k stars) is the nearest *product* match** and the only "high" overlap row:
   multiple active branches in one working directory, per-lane staging, agent docs that route each
   agent session onto its own branch and tell the agent to "split independent work out of the
   current session". The routing is done by a human dragging lanes or by the agent being told to
   do it — not inferred from the tree.

**The real gap, stated plainly.** Every tool in this bucket assumes *one actor who knows what they
were doing*. The hunk→destination mapping is either supplied by that actor (staging UIs, StGit,
`jj split`), or inferred from **git history of that one branch** (git-absorb, jj absorb), or
supplied by **path metadata** (diff-split), or by an LLM asked to be sensible (the 2026 AI
splitters). What does not exist anywhere in this bucket is:

- inferring **feature/session identity** for hunks that have no commit yet and no path signal —
  i.e. attributing work to *which agent session touched it*, not to which historical commit;
- doing that across **N concurrent sessions sharing one dirty tree**, where the sessions are
  different vendors and none of them declares itself;
- **predicting hunk/line-range overlap between those sessions before a merge**, rather than
  discovering it afterwards (git-imerge discovers per-commit-pair conflicts after the fact;
  GitButler hands the overlap decision to the human);
- emitting a **grounded, code-extracted brief** of what the other work is, so a drafting LLM cannot
  invent it;
- and doing all of it **stdlib-only, daemonless, read-only, agent-neutral**, inside a repo that
  someone else already dirtied — which is precisely why GitButler/diff-split/git-splice do not
  qualify even though their mechanics overlap.

So the honest framing for the README: *the primitives (hunk addressing, provenance-based
assignment, branch fan-out by cherry-pick) are all prior art, individually, some of them at
20-80k stars. The composition — multi-session attribution of an uncommitted tree feeding
provenance-style hunk assignment into per-feature branch creation, with pre-merge hunk collision
prediction — is not implemented by anything found.*

## Surprises / collisions

1. **GitButler is the real threat to capability 5's novelty.** 21.8k stars, pushed the day before
   this survey, and its own docs now describe our scenario in agent terms: several agent sessions
   sharing ONE working directory, each session's work routed onto its own branch, stacked branches
   for dependencies, and the explicit "starting from a single working directory ⇒ the extracted
   branches merge cleanly" argument. Our delta is narrower than "nobody does this".
2. **`diff-split` already produces the exact artifact we claim to produce** — one big diff → N clean
   PR branches, local git only, patch snapshots, a "session branch", cherry-pick per batch. 3 stars,
   6 months old, monorepo-codemod framing, but the README's output contract *is* our output
   contract. Must be cited by name.
3. **`git-splice` independently invented our hunk-grouping mechanism, in stdlib-only Python, eight
   days before this survey.** Hunk-adjacency + shared-identifier graph → deterministic clustering of
   a *working-tree* diff. 0 stars, one-day repo, commits not branches — but a reviewer will point at
   it, so we should cite it first and state the delta ourselves.
4. **`git-hunk-tool` (inside claude-split-commits) already ships the "individually addressable hunks
   with fingerprints, staged via `git apply --cached`" library layer** we would need, as a Claude
   Code skill. Vendor-bound, single session.
5. **A 2026 micro-cluster of AI commit splitters has made "AI groups a messy tree into logical
   commits" sound like a commodity** (Splitify, ncomm, ai-split-commit.nvim, git-agent-cli, commity,
   aicommit-split, agentic-commit-splitter, auto-commit-splitter, split-git-commits,
   ai-conventional-commit-cli). Individually 0-4 stars (git-agent-cli 81), but Splitify's README
   already states the multi-agent mess as the motivation ("40 files across three different
   architectural layers" after a Copilot session). Our novelty cannot rest on intent-grouping.
6. **aider is the strongest existing session-attribution mechanism in an agent harness** — it
   rewrites git author/committer metadata with "(aider)" and pre-commits dirty files. That is
   capability 2 prior art, and it is *already deployed at 49k stars*. It also shows the opposite
   strategy: absorb the whole dirty file into one commit rather than split it.
7. **git-imerge does not belong in this bucket's threat model.** Verified: it is per-commit-pair
   conflict isolation between committed branches, needs a clean tree, last pushed 2024-07-17.
   Cite it as "splits merges, not working trees".
8. **`git stash push -p` + `git stash branch` is the built-in we must beat on novelty**, not on
   convenience. Any reviewer can assemble our demo in six manual commands. Our claim has to be the
   automatic attribution + collision detection, not the branch creation.
